# Архитектура

Клиент: HTML/CSS и JavaScript, Canvas для воспроизведения событий. Django предоставляет JSON API, сессионную авторизацию, CSRF-защиту и административный интерфейс. PostgreSQL — рабочая база, SQLite — локальная разработка. SimPy исполняется отдельным процессом simulation_worker. PDF формируется ReportLab с локальным шрифтом DejaVu, Excel — openpyxl. Внешние CDN, LLM и API не требуются для демонстрации.

## Данные

- Product: уникальный source_id, карточка, price, specs, список applications, sources, полный набор исходных observations.
- Normative: ключ, значение, подпись, источник и дата обновления; набор типов и диапазонов задаёт schema.py.
- Project: владелец, название, текущая ревизия, снимок входов и результата.
- ProjectVersion: неизменяемая запись каждой сохранённой ревизии; уникальный ключ project + revision.
- SimulationRun: владелец или сессия гостя, состояние очереди, расчётный снимок, события и показатели, срок хранения 24 часа.
- LoginAttempt: ограничение повторных неудачных входов по хешу IP + имени.

Пользовательский запрос результата всегда ограничен владельцем. Обновления проектов используют блокировку и проверку revision для защиты от потери изменений в другой вкладке. Экспорт сохранённой ревизии читает снимок, поэтому редактирование каталога не меняет старый отчёт. Загруженные Excel/CSV обрабатываются в памяти, исходные файлы не сохраняются. Удаление проекта каскадно удаляет версии.

## Очередь

Веб-процесс сохраняет задание и возвращает HTTP 202. Отдельный worker выбирает pending-запись транзакционно, вычисляет и сохраняет результат. PostgreSQL использует SELECT FOR UPDATE SKIP LOCKED для нескольких worker. В SQLite запускается один worker. Прерванные running-задания старше 3 минут помечаются failed. Старые задания удаляются через 24 часа. Для одного пользователя/гостевой сессии разрешён один активный прогон, общий предел очереди — 50.

## Расширение

Новые виды объектов добавляются в data/objects.json; для полного расчёта требуется отдельный модуль процесса с входной схемой и источниками, а не применение складской формулы к медицине или аэропорту. Новый модуль должен возвращать общий контракт сценариев, вложений, затрат, денежного потока и объяснений.

Реальные интеграции WMS/ERP/1С могут заполнять тот же контракт входов, адаптер каталога — Product, мониторинг оборудования — фактические распределения времени симуляции. Все подключаемые данные должны сохранять дату, источник, единицы и статус подтверждения. Промышленные интеграции, реестры и субсидии не реализованы, поскольку не входят в согласованный MVP.

## Безопасность и эксплуатация

Пароли хеширует Django, проектные API требуют авторизации, изменяющие запросы проверяют CSRF. DEBUG выключен в Docker. Внешний доступ — только HTTPS через Caddy. База и web не публикуют порты на хост. Секреты — в .env, исключённом из Git и Docker image. Загрузка ограничена 5 МБ, распакованный XLSX — 30 МБ; формулы файла не исполняются. Строки внешнего каталога экранируются перед выводом в HTML и Excel.

Проверки и ограничения эксплуатации описаны в DEPLOYMENT.md и RELEASE_CHECKLIST.md. Целевой сервер необходимо нагрузочно проверить отдельно от локального запуска.
